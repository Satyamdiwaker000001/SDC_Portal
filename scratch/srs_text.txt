1. Introduction
1.1 Purpose
The Software Development Cell (SDC) Portal is a centralized web-based platform designed to streamline the management of student software development activities within the Software Development Cell of the institution.
The portal provides an integrated environment for managing users, recruitment, teams, projects, software development lifecycle (SDLC) activities, task assignment, project documentation, communication, progress tracking, and performance evaluation.
The primary objective of the system is to replace manual project management processes with a structured, transparent, and real-time collaborative platform that supports the complete software development workflow from recruitment to project completion.
The portal also serves as a centralized repository for software engineering documentation and enables standardized project execution by following predefined Software Development Life Cycle (SDLC) phases.
This Software Requirements Specification (SRS) document has been restructured to conform to the IEEE 830 recommended practice for SRS documents (aligned with ISO/IEC/IEEE 29148), so that requirements are unambiguous, verifiable, traceable, and directly usable by designers, developers, and testers.
1.2 Document Conventions
The following terminology is used consistently throughout this document to express the strength of a requirement, following RFC 2119-style conventions adapted for IEEE 830:
Shall — indicates a mandatory (binding) system requirement.
Should — indicates a strongly recommended implementation choice.
May — indicates an optional capability.
Can — indicates an available system capability or a statement of fact.
Requirement identifiers follow a fixed, traceable numbering scheme:
FR-xxx — Functional Requirement
NFR-xxx — Non-Functional Requirement
BR-xxx — Business Rule
SR-xxx — Security Requirement
AC-xxx — Acceptance Criterion
Headings are numbered hierarchically (Section.Subsection.Sub-subsection). All requirement tables list the unique ID in the left column and the requirement statement in the right column so that each requirement can be traced independently in a requirements-traceability matrix (RTM).

1.4 Product Scope
The SDC Portal provides a centralized management system for all operational activities of the Software Development Cell. The system supports three authenticated user roles: Administrator, Mentor, and Developer. A Developer may additionally be designated as a Team Leader with extended permissions; Team Leader is a designation, not an independent account role.
The portal delivers the following in scope capabilities: User Authentication, Recruitment Management, User Management, Team Management, Project Management, SDLC-based Task Management, Task Assignment, Mentor Verification, Project Documentation Management, Progress Tracking, Performance Evaluation, Real-Time Notifications, Leaderboards, Announcements and Notices, Alumni Management, and Audit Logging.
The portal also includes a publicly accessible landing page containing organizational information, member profiles, completed projects, recruitment details, and general information about the Software Development Cell.
The objectives that this product is intended to achieve are:
Establish a standardized project management process for all SDC projects.
Improve collaboration among Administrators, Mentors, Team Leaders, and Developers.
Track project progress in real time.
Maintain software engineering documentation in a centralized repository.
Encourage accountability through transparent task assignments and performance tracking.
Improve project quality through Mentor verification before task completion.
Maintain complete historical records of projects and developer contributions.
Automate repetitive administrative activities such as recruitment approval, user account generation, alumni conversion, and progress reporting.
Provide an industry-oriented software development workflow based on predefined SDLC phases.
Promote professional software engineering practices within the Software Development Cell.

2. Overall Description
2.1 Product Perspective
The SDC Portal is a new, self-contained, centralized web-based application developed to digitize and streamline all operational activities of the Software Development Cell. It is not a component of a larger system and has no dependency on a pre-existing legacy system; it replaces informal, manual coordination (spreadsheets, chat groups, verbal reporting) with a single system of record.
The portal integrates recruitment management, user management, team formation, project execution, SDLC-based task management, documentation management, communication, progress monitoring, and performance evaluation into a single platform.
The system follows a structured organizational hierarchy consisting of Administrators, Mentors, Team Leaders, and Developers. Each user interacts with the system according to predefined responsibilities and permissions enforced through Role-Based Access Control (RBAC).
The portal is designed specifically for the Software Development Cell operating under the academic structure followed by Dr. A.P.J. Abdul Kalam Technical University (AKTU).
The application consists of two major sections:
Public Landing Website — unauthenticated, publicly accessible.
Authenticated Internal Management Portal — secured, role-restricted operational functionality.

2.3 User Classes and Characteristics
The SDC Portal provides role-based access to its users. Every authenticated user is assigned exactly one predefined role with specific responsibilities and permissions. Team Leader is a designation layered on top of the Developer role rather than a distinct account type.
2.3.1 Administrator
The Administrator is the highest-privileged user and is responsible for the complete operation of the Software Development Cell through the portal.
Responsibilities: manage user accounts; manage recruitment; create and manage teams and projects; assign Mentors and Team Leaders; monitor project progress and developer performance; publish notices and announcements; review reports and analytics; manage alumni conversion; access project documentation; monitor audit logs.
Characteristics: full system access and the highest level of authority; does not create or assign project tasks; does not verify completed tasks.
2.3.2 Mentor
A Mentor supervises one or more assigned teams and ensures project activities progress according to schedule.
Responsibilities: monitor assigned teams and project progress; verify or reject completed tasks; publish announcements to assigned teams; forward administrative communication; review project documentation.
Characteristics: may supervise multiple teams; may verify completed tasks; does not create projects, teams, or tasks.
2.3.3 Developer
A Developer implements assigned project tasks and contributes to software development activities.
Responsibilities: complete assigned tasks; participate in project development; view project documentation; track assigned work; view notices/announcements; maintain personal profile.
Characteristics: belongs to exactly one active team; may be assigned multiple tasks; does not assign tasks, manage projects, or verify completed tasks.
2.3.4 Team Leader (Developer designation)
A Team Leader is a Developer with additional project management responsibilities and is not an independent user role.
Responsibilities: create project tasks; assign tasks to Developers; manage SDLC tasks; monitor team progress; update task status; upload project documentation; maintain the project GitHub repository link.
Characteristics: must be a Final Year Developer; belongs to one active team; manages only the assigned team's project; does not verify completed tasks.
2.3.5 Applicant
An Applicant is a student who has submitted a recruitment application. Responsibilities: submit the application; await review. Characteristics: has no portal access; becomes a Developer after administrative approval.
2.3.6 Alumni
An Alumni is a former SDC member whose membership has been converted from Active to Alumni. Characteristics: appears on the Landing Page under Former Members; historical contributions remain preserved; cannot receive new task assignments, participate in active projects, or access the internal portal.
2.4 Operating Environment
Client Environment
The portal shall be accessible through modern web browsers: Google Chrome, Microsoft Edge, Mozilla Firefox, and Safari (latest stable versions). The user interface shall support desktop, laptop, tablet, and mobile devices through responsive web design.
Server Environment
The application shall operate on a Linux-based server environment. Recommended deployment stack: Ubuntu Server, Docker, Nginx, FastAPI, MySQL.
Database Environment
The portal shall use MySQL as the primary relational database management system. The database shall be fully normalized to maintain data consistency, integrity, and scalability.

2.5 Design and Implementation Constraints
Academic Constraint
The portal is specifically designed for the Software Development Cell operating under the academic calendar followed by Dr. A.P.J. Abdul Kalam Technical University (AKTU).
Alumni Conversion Constraint
The automatic Alumni conversion process shall execute every year on 31 July at 23:59:59 (server time).
Team Structure Constraint
Each active team shall contain exactly one Mentor, exactly one Team Leader, and one or more Developers.
Project Constraint
Each project shall be assigned to one team. A project may be created before team assignment, and a team may be created before project assignment; the assignment remains editable by the Administrator until explicitly modified.
Task Management Constraint
Only the Team Leader shall create, assign, and manage project tasks. Administrators, Mentors, and standard Developers shall not perform task management activities.
Documentation Constraint
Each project shall maintain the following mandatory software engineering documents: Product Requirements Document (PRD), Business Requirements Document (BRD), Software Requirements Specification (SRS), Use Case Document, Use Case Diagrams, Workflow Document, Data Flow Diagram (DFD), Entity Relationship Diagram (ERD), Database Design, API Documentation, Frontend Documentation, Backend Documentation, Deployment Guide, Testing Documentation, User Manual, and Developer Guide.
Authentication Constraint
Only authenticated users shall access the internal portal. The Landing Page and Recruitment Form shall remain publicly accessible.
2.6 User Documentation
The portal shall provide the following documentation for its different categories of users: Administrator Guide, Mentor Guide, Developer Guide, User Manual, Installation Guide, Deployment Guide, API Documentation, and Project Documentation. All documentation shall be maintained within the Project Documentation Repository and updated whenever significant system modifications are introduced.

Every Developer belongs to only one active team.

4. External Interface Requirements
This section, added in accordance with IEEE 830 §3.1, describes the interfaces between the SDC Portal and its users, hardware, other software, and communication channels. These interfaces were implicit in the original requirements set and are made explicit here for design and integration purposes.
4.1 User Interfaces
The portal shall present a public Landing Page (unauthenticated) and a role-specific dashboard for each authenticated role (Administrator, Mentor, Developer/Team Leader).
All authenticated screens shall share a consistent navigation shell (sidebar/top bar) showing the current user's role, notifications, and quick links to modules permitted for that role.
Forms (recruitment application, task creation, document upload, notice/announcement composition) shall provide inline field-level validation messages before submission.
The UI shall be responsive and shall render correctly on desktop, laptop, tablet, and mobile viewport widths.
Data tables (task lists, leaderboards, audit logs) shall support sorting and, where the record count is large, pagination or infinite scroll.
Destructive or state-changing actions (Alumni conversion, task rejection, account deactivation) shall require an explicit confirmation step.
Wireframes and a detailed visual style guide are outside the scope of this SRS and shall be maintained in the UI/UX design specification referenced from the Documentation Repository.
4.2 Hardware Interfaces
The SDC Portal is a purely web-based application and has no direct interface to specialized hardware devices. The following general hardware assumptions apply:
Client hardware: any desktop, laptop, tablet, or smartphone capable of running a supported modern web browser with a stable internet connection.
Server hardware: a Linux-capable host (physical or virtual/cloud instance) with sufficient CPU, memory, and disk to run the containerized application stack and the MySQL database.
No proprietary peripherals, sensors, or embedded devices are required for standard operation.
4.3 Software Interfaces
Interface
Description
MySQL RDBMS
Primary system of record for all portal data (users, teams, projects, tasks, documentation metadata, performance, audit records), accessed via SQLAlchemy ORM from the FastAPI backend.

Single-page application that consumes the REST API and renders the Landing Page and authenticated dashboards.

4.4 Communications Interfaces
All client-server communication shall occur over HTTPS (TLS-encrypted HTTP) to protect credentials and data in transit.
The REST API shall exchange data using JSON payloads.
Authenticated sessions shall be represented using a secure, signed token (e.g., JWT) transmitted via HTTP headers or secure cookies.
Real-time notification delivery shall use a persistent or near-real-time channel (e.g., WebSocket or short-interval polling); the specific transport is a design decision to be finalized in the technical design document.
No email, SMS, or third-party push-notification gateway is required for the initial release; these are listed under Future Scope (Appendix B).

6. Business Rules
The following business rules define the operational policies of the SDC Portal. Business rules are domain policies that constrain or trigger functional behavior across multiple features; they are mandatory and shall be enforced throughout the system.
6.1 Consolidated Business Rules
ID
Requirement
BR-001
The portal shall support the authenticated user roles Administrator, Mentor, and Developer. Team Leader is not a separate user role and shall be designated from an existing Developer.
BR-002
Only authenticated users shall access the internal portal; public users shall only access the Landing Page and Recruitment Form.
BR-003
A Developer shall belong to only one active team at any given time and shall not be assigned to multiple active teams simultaneously.
BR-004
A Mentor may supervise one or more teams; each team shall have only one assigned Mentor.
BR-005
Each team shall have exactly one Team Leader, selected from the Developers belonging to that team, who shall be a Final Year Developer.
BR-006
Each project shall be assigned to one team. A project may exist before team assignment and a team may exist before project assignment; the Administrator may update the project-team assignment whenever required.
BR-007
Every project shall automatically contain the predefined SDLC phases (Planning, Analysis, Design, Development, Testing, Deployment, Maintenance), which are system-defined and shall not be created, deleted, renamed, or reordered by users.
BR-008
Only the Team Leader shall create, edit, assign, and manage project tasks. Administrators, Mentors, and standard Developers shall not manage project tasks.
BR-009
Every task shall belong to exactly one SDLC phase and shall be assigned to exactly one Developer; a Developer may be assigned multiple tasks.
BR-010
Every task shall maintain one of the statuses Pending, In Progress, or Completed; task status shall be updated only by the Team Leader.
BR-011
Every completed task shall require Mentor verification; a completed task shall not be considered officially completed until verified by the assigned Mentor.
BR-012
The Mentor may only Verify or Reject a task. If rejected, the task shall automatically return to the In Progress status.
BR-013
Developer, Team, Project, and SDLC Phase progress shall be calculated only from Mentor-verified tasks; tasks awaiting verification shall not contribute to progress calculations.
BR-014
Developer and Team performance shall consider the number of verified completed tasks, task completion percentage, task completion before due date, and overall project contribution, updated automatically after Mentor verification.
BR-015
The portal shall maintain a Developer Leaderboard and a Team Leaderboard, updated automatically based on verified performance data.
BR-016
Official communication shall follow the defined authority hierarchy (Administrator → Mentor → Team Leader → Developers) and shall not bypass this hierarchy.
BR-017
Project-related document requests shall flow: Administrator requests the Mentor → Mentor forwards to the Team Leader → Team Leader submits to the Mentor → Mentor reviews and forwards to the Administrator.
BR-018
Recruitment availability shall be controlled only by the Administrator; when recruitment is disabled, the recruitment form shall not accept new applications.
BR-019
After approval of a recruitment application, the system shall automatically create the Developer account, generate the User ID and initial password, and export credentials in CSV format.
BR-020
The system shall automatically convert eligible Final Year Developers to Alumni every year on 31 July at 23:59:59; the Administrator may also manually convert Developers to Alumni or restore Alumni to Active status.
7. Other Requirements
7.1 Legal, Compliance, and Institutional Requirements
The portal shall operate in accordance with the academic policies and calendar of Dr. A.P.J. Abdul Kalam Technical University (AKTU), as referenced in Section 2.5.
Applicant and Developer personal data (name, email, mobile number, resume) shall be treated as institutionally sensitive data and shall be restricted per Section 5.3 (Security Requirements).
Retention of historical records (Section 2.7, 6.20) shall follow institutional record-keeping policy; no automatic deletion of historical project or performance data is permitted.
7.2 Reuse and Extensibility Objectives
The RBAC model shall be designed so that additional roles (e.g., a future "Reviewer" or "Alumni Mentor" role) can be added without redesigning the authorization layer (see NFR-018).
The SDLC phase model, while fixed for this release, shall be stored as configurable data rather than hard-coded logic, to support a future configurable-phase capability without a schema change.
API endpoints shall follow REST conventions and versioning so that the future Mobile Application (Appendix B) can reuse the same backend without duplication.
7.3 Open Items (To Be Determined)
TBD-1: Exact concurrent-user and response-time targets for NFR-001/NFR-005 are to be finalized after load-testing during the design phase.
TBD-2: The real-time notification transport (WebSocket vs. polling interval) referenced in Section 4.4 is to be finalized in the technical design document.
TBD-3: Backup frequency and retention period for NFR-037–039 are to be defined by institutional IT policy.
